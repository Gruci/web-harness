웹 개발용 하네스 v4.0.1

## 3줄 요약

1. Claude Code나 Codex와 개발할 때 세션이 바뀌어도 같은 작업 절차와 개발 규칙을 사용합니다.
2. **자동 검사**가 편집 후 위반을 알려주고, 연결된 종료 훅이 수정과 재검증을 요구합니다.
3. 첫 코드 전에 AI와 언어 및 업무 분류를 정하고, 새 경계가 필요할 때만 제안을 검토합니다.

## 어떤 도구인가요?

초보 운전자가 실수해도 차가 알아서 멈추는 **자동 브레이크**를 떠올려 보세요. 이 도구는 AI가 규칙을 벗어난 코드를 쓰면 편집 직후 위반을 알려주고 스스로 고치게 만드는, 개발용 가드레일입니다.

AI랑 대화하다 보면 코드가 꼬입니다. 어제 합의한 규칙을 오늘 세션은 모르고, "이 정도는 괜찮겠지"가 쌓이다 보면 어느새 아무도 못 읽는 코드가 됩니다. 규칙을 문서로 적어두는 것만으로는 막을 수 없습니다 — 문서는 부탁일 뿐, 강제가 아니니까요. 이 하네스는 규칙을 **차단**으로 구현합니다.

### Claude Code와 Codex에서 함께 사용

개발 규칙과 작업 절차, 검사 엔진을 공유합니다.
에이전트별 진입점과 도구 설정은 분리합니다.
공통 절차는 [작업 절차 허브](dev/workflows/README.md), 실행 계약은 [하네스 지도](dev/HARNESS.md)에 있습니다.

Codex의 첫 초기화는 `python -X utf8 setup_global_permissions.py --agent codex`로 합니다.
양쪽을 한 번에 초기화하려면 `--agent both`를 사용합니다.
도구 승인 없이 실행하도록 전역 설정을 설치하며 질문은 중요한 모호함의 확정과 구현 전 계획 승인으로 제한합니다.
기존 설정 보존과 적용 범위는 [전역 자율 실행 계약](dev/HARNESS.md#전역-자율-실행-초기화)을 따릅니다.
Codex 전역 설정 설치는 Python 3.11 이상을 권장합니다.
Python 3.10에서는 설치된 `toml` 패키지가 필요합니다.
새 세션에서 적용하며, 호스트 앱이 강제하는 정책은 전역 설정보다 우선합니다.

설치 후 `python -X utf8 harness_install.py --check-agents`로 양쪽 연결을 검사합니다.
Codex 훅은 런타임의 신뢰 검토를 마쳐야 실행됩니다.
현재 호스트의 훅 지원을 확인하고 임시 체크아웃에서 위반을 검출하는지 확인합니다.
이 확인 전에는 저장·종료 차단이 활성화됐다고 간주하지 않습니다.

### 로컬 파일과 비밀값

환경변수 파일, 가상환경, 의존성, 로컬 DB와 로그는 `.gitignore`로 제외합니다.
비밀값을 제거한 `.env.example` 같은 설정 예제와 의존성 lockfile은 공유합니다.
SQL 소스와 마이그레이션은 추적 대상으로 유지합니다.
이미 추적 중인 파일에는 ignore 규칙이 소급 적용되지 않으므로 커밋 전 staged diff를 확인합니다.

### 쓰기 전 / 쓴 후

| | 쓰기 전 | 쓴 후 |
|:--|:--|:--|
| 세션이 바뀌면 | 지난 합의를 잊고 제멋대로 작성합니다 | 세션과 무관하게 같은 규칙이 강제됩니다 |
| 규칙을 어기면 | 아무 일도 없습니다 — 나중에 사람이 발견합니다 | 편집 직후 위반을 알려주고 AI가 수정합니다 |
| 코드 작성 순서 | 요청하자마자 바로 구현합니다 | 설계서를 승인하기 전에는 소스에 손대지 못합니다 |
| "다 됐어요" | 말뿐일 수 있습니다 | 전 검사를 통과해야 세션이 끝납니다 |
| 검사가 안 돌 때 | 조용히 통과한 것처럼 보입니다 | "안 돌았다"고 사유와 함께 보고됩니다 |

### 개발을 잘 몰라도 괜찮습니다 — 오히려 가장 필요한 분입니다

개발자는 AI가 이상한 코드를 쓰면 눈으로 알아챕니다. 개발을 모르면 "다 됐습니다"라는 말을 믿는 수밖에 없죠. 그런데 AI만 믿고 만든 프로젝트는 대개 이런 길을 갑니다.

1. 처음 며칠은 마법 같습니다. 말만 하면 기능이 생깁니다.
2. 코드가 쌓이면 AI가 자기가 만든 코드에 발이 걸리기 시작합니다. 기능 하나를 고치면 멀쩡하던 다른 곳이 깨집니다.
3. 어느 순간 "이 기능 추가해줘"가 더 이상 통하지 않고, 고치는 것보다 처음부터 다시 만드는 게 빠른 지경이 됩니다. 그동안 쓴 시간과 비용은 돌아오지 않습니다.

이 도구는 그 2번 단계가 오지 않게 막습니다. 코드를 읽을 줄 아는 사람이 옆에서 매번 검사해주는 것과 같은 효과를, 자동 검사가 대신합니다. AI의 "다 됐습니다"는 검사를 통과했을 때만 인정되고, 통과 못 하면 AI가 스스로 고칠 때까지 세션이 끝나지 않습니다. **코드를 볼 줄 몰라도, 코드가 무너지지 않습니다.**

### 이럴 때 쓰세요

- **개발을 모르지만** AI로 서비스를 만들고 있고, 어느 날 갑자기 멈출까 불안할 때
- Claude Code로 **프로젝트를 처음부터** 만들려는데, 코드가 산으로 갈까 걱정될 때
- AI와 오래 협업하며 **일관성이 무너지는 것**을 이미 겪어본 개발자
- "설계 먼저, 구현은 승인 후" 흐름을 **말이 아니라 시스템으로** 강제하고 싶을 때

웹 서비스와 API 서버 및 배치 작업에 맞춰 구성할 수 있습니다. 선택한 언어의 소스 수집과 분석기를 연결해야 하며 미지원 검사는 미검증으로 남습니다.

### 1단계 — 받기

```bash
git clone https://github.com/Gruci/web-harness.git my-project
cd my-project
rm -rf .git && git init && git add -A && git commit -m "init"
```

### 2단계 — Claude Code 안에서 설치

```bash
claude
```

세션이 열리면 이렇게 말해보세요.

```
하네스 깔아줘
```

온보딩이 몇 가지를 물어봅니다 — 기술 용어가 아니라 "무엇을 만들고 싶은가요?" 수준입니다. 화면이 있는 서비스인지, API만 있는지, 주기적으로 도는 작업인지 정도만 답하면 설정 파일 생성, GitHub 연결, 검사 활성화까지 알아서 끝납니다. 기술 스택을 아직 못 정했어도 괜찮습니다. 후보마다 무엇이 달라지는지 도구가 설명해 주고, 고르는 것은 당신입니다.

### 3단계 — 그냥 개발하세요

```
로그인 기능 만들어줘
```

이제 AI는 바로 코드를 쓰지 않습니다. 먼저 무엇을 어떻게 만들지 설계서 파일로 정리해 보여주고, 당신이 승인해야 구현을 시작합니다. 구현 중에는 파일을 저장할 때마다 검사가 돌고, 위반이 있으면 AI가 스스로 고칩니다. 세션을 끝낼 때도 전체 검사를 다시 돌아서, 미해결 위반이 남아 있으면 종료되지 않습니다.

여기까지가 전부입니다. 아래부터는 필요할 때 찾아보는 내용입니다.

## 프로젝트 설정과 분류 정본

서식 3의 프로파일은 선택한 언어와 기술 검사 경로를 연결합니다.
컴포넌트의 이름과 책임 및 허용 의존은 별도 그래프에서 관리합니다.
첫 코드 전에 AI가 분류를 제안하고 사용자의 실제 답변을 기록합니다.
기존 승인 범위의 편집은 질문을 반복하지 않습니다.

```python
PROFILE_SCHEMA = 3
LANG = None
COMPONENT_GRAPH = "docs/architecture/components.json"
CHECK_PATHS = {"ui": None, "tests": None}
```

LANG이 미정이면 Python이나 Go를 자동 선택하지 않습니다.
선택한 언어의 검사 도구까지 연결한 뒤 제품 코드를 작성합니다.
[분류 계약](dev/COMPONENTS.md)과 [조립 절차](dev/workflows/harness-assembly.md)를 따릅니다.
[작동 예시](examples/harness-reference/README.md)는 한 사례이며 프로젝트의 기본 스택을 강제하지 않습니다.

사용자 답변 대기는 완료가 아닙니다.
Stop은 제안을 알리고 정상 대기를 허용하며 관련 없는 작업은 계속할 수 있습니다.

## 일상 개발은 이렇게 흘러갑니다

기능을 요청하면 다음 5단계를 거칩니다. 당신이 개입하는 지점은 **질문에 답하기**와 **설계서 승인** 두 곳뿐입니다.

```
[1. 질문·분석] → [2. 설계서 작성] → [3. 승인 대기] → [4. 구현·검사] → [5. 정리·재검증]
                                          ▲
                                     당신이 개입하는 지점
```

| 단계 | 일어나는 일 | 소스 변경 |
|:--:|:--|:--:|
| 1 | 적용 화면, 사용 데이터, 작업 범위를 물어봅니다. 관련 코드를 직접 열어 데이터 흐름을 분석합니다 | 없음 |
| 2 | 설계서를 파일로 만듭니다. 정확한 파일 경로, 실제 코드 조각, 예상 파급 범위가 들어갑니다 | 없음 |
| 3 | 당신의 검토와 승인을 기다립니다 | 없음 |
| 4 | 승인된 설계서대로 구현합니다. 저장할 때마다 검사가 돕니다 | 발생 |
| 5 | 관련 문서를 갱신하고 작업 파일을 정리합니다. 종료 시 전체 검사를 다시 돕니다 | 발생 |

설계서에 `TBD`, "나중에 구현", "위와 유사하게" 같은 미확정 표현이 있으면 설계서로 인정되지 않고 반려됩니다. 화면 시안이 필요한 작업은 `docs/tasks/mockup/`에 시안 파일을 먼저 만들어 승인받고, 승인된 시안 그대로 구현합니다. 작업이 끝나면 조사·설계·시안 파일이 함께 `docs/tasks/archive/`로 정리됩니다.

## 자주 묻는 질문

**파이썬이 아닌 언어에서도 쓸 수 있나요?**
언어팩은 소스 수집과 도구 연결을 돕습니다. 팩을 선택했다는 사실만으로 모든 컴포넌트 분석을 지원하지는 않습니다. 구문 분석과 포트 계약 실행까지 확인하며 지원하지 않는 검사는 `[TOOL]`로 보고합니다. 완료 검증은 미검증을 성공으로 처리하지 않습니다.

**기술 스택을 못 정했는데 설치해도 되나요?**
네. 온보딩은 기술명이 아니라 만들려는 것의 형태를 물어봅니다. 미정이면 언어를 고정하지 않으며 첫 코드 전에 사용자와 스택 및 분류를 정합니다.

**화면이 없는 서비스인데 화면 검사가 "설정 미비"로 계속 표시됩니다.**
`ARCH = "backend_only"`(서버만 있음) 또는 `ARCH = "headless"`(웹·화면 모두 없음)를 선언해 보세요. 해당 검사들이 `[SKIP]`(설정을 안 채움)이 아니라 `[N/A]`(이 프로젝트 형태에는 채울 것이 없음)로 보고됩니다. 잃은 것과 원래 없는 것이 출력에서 구분됩니다.

**설치 후에 프로젝트 성격이 바뀌면요?**
`harness_profile.py`의 해당 항목만 고치면 됩니다. 화면 없이 시작했다가 화면을 추가하는 경우 `ARCH`를 `web_layered`로 바꾸고 `CHECK_PATHS["ui"]` 한 항목을 적으면 화면 관련 검사 7종이 대상을 모으기 시작합니다.

**특정 검사가 우리 프로젝트에 안 맞으면 끌 수 있나요?**
해당 설정 항목을 비우면 `[SKIP]` 상태가 됩니다. 다만 쉰다는 사실은 매 실행마다 사유와 함께 출력되고, 이를 숨기는 설정은 일부러 만들지 않았습니다.

**하네스 자체는 어떻게 업데이트하나요?**
`python -X utf8 harness_install.py --check-update`가 원류의 버전과 대조해 알려만 줍니다. 설치본은 그대로입니다. 올리기로 했으면 작업 트리를 깨끗하게 만든 뒤 `--upgrade`를 실행합니다 — 검사 엔진(`kernel/`)과 Claude 훅(`.claude/hooks/`)과 프리셋 원류 파일을 갈아끼우고 프로젝트에서 추가한 파일은 보존합니다. 설정 파일, 문서, 저장소 전용 검사, 그림은 프로젝트 것이라 손대지 않습니다. 끝나면 양쪽 에이전트 연결 진단을 실행합니다.
설정·스킬·공통 절차에 새로 생긴 항목은 자동 병합되지 않습니다. `git diff`를 보고 필요한 것만 직접 옮긴 뒤 진단을 다시 실행합니다.

**개발자가 직접 써야 하는 건 뭔가요?**
설치 시점에는 없습니다. 폴더명과 프레임워크 함수명은 온보딩이 처리합니다. 개발자만 아는 것은 그 서비스의 도메인 지식이고, `PROJECT.md`에 개발하면서 조금씩 쌓으면 됩니다.

**GitHub 저장소를 미리 만들어야 하나요?**
`gh` 인증이 돼 있다면 비공개 저장소를 자동으로 만들어 푸시합니다. 공개 저장소는 되돌리기 어려우므로 명시적으로 요청할 때만 만듭니다. 인증이 없을 때만 저장소 주소를 물어봅니다.

**모바일 앱으로 확장할 계획이 있다면요?**

<details>
<summary>화면을 포함하는 프로젝트의 앱 이식 대비 규칙</summary>

현재 개발 기준은 웹입니다. 다만 앱으로 옮길 때 재사용할 것과 버릴 것이 미리 구분되도록, 재사용 대상을 초기부터 분리해 둡니다.

| 규칙 | 이식할 때 |
|:--|:--|
| 계산·데이터 가공을 화면 파일 밖에 두기 | 로직 그대로 이동 |
| 색상·간격·글자 크기를 정본 파일에서만 참조 | 값 그대로 재사용 |
| 브라우저 전용 기능은 단일 래퍼 경유 | 그 파일만 교체 |
| 페이지 이동 코드를 페이지 계층에 한정 | 교체 범위 최소화 |

앱을 만들게 되면 화면 계층만 다시 구현하고 서버·로직·디자인 값은 그대로 가져갑니다. 앱을 안 만들어도 손해는 없습니다 — 이 분리는 그 자체로 좋은 구조니까요.

## 상세 정보

여기부터는 동작 원리가 궁금할 때 읽는 내용입니다. 사용하는 데 꼭 필요하지는 않습니다.

### 설계 원칙

| 원칙 | 구현 방식 |
|:--|:--|
| **설계 우선** | 코드 작성 전 설계서를 파일로 만들고 승인을 받습니다. 승인 전에는 소스가 변경되지 않습니다 |
| **저장 시점 검증** | 파일 저장 직후 정적 검사가 돌고, 위반 시 그 변경을 차단하고 수정을 요구합니다 |
| **종료 시점 재검증** | 대화 종료 시 전체 검사를 다시 돕니다. 미해결 위반이 있으면 세션이 끝나지 않습니다 |
| **스택 비종속** | 판정 로직은 프로젝트를 모릅니다. 프로젝트별 값은 설정 파일 한 곳에 격리됩니다 |
| **미검증은 미검증으로 보고** | 언어·설정 때문에 못 돈 검사는 통과가 아니라 `[SKIP]`으로, 사유와 함께 출력됩니다 |

### 검사 결과와 완료 판정

수행하지 못한 사유를 셋으로 나눈 것이 이 도구의 핵심입니다 — 각각 해야 할 일이 다르기 때문입니다.

| 등급 | 의미 | 할 일 | 세션 종료 |
|:--|:--|:--|:--:|
| `[OK]` | 수행했고 위반 없음 | — | 허용 |
| `[SKIP]` | 설정이 없어 안 돌았음 | 설정을 채우면 활성화 | 허용 |
| `[N/A]` | 이 언어·프로젝트 형태에서 규칙이 성립하지 않음 | **없음 — 손실이 아닙니다** | 허용 |
| `[TOOL]` | 필수 도구나 분석기를 실행하지 못함 | 검사 환경을 연결 | --verify 종료 코드 2 |
| `[FAIL]` | 위반 검출 | 수정 | 차단 |
| `[REPORT]` | 오탐 가능성이 있는 연성 신호 | 판단 | 허용 |
| `[DECISION]` | 분류에 사용자 결정 필요 | 제안에 답변 | 종료 코드 3, 정상 대기 |

> **`[SKIP]`은 통과가 아닙니다.** 이전 세대 도구는 이 상태를 통과로 처리했고, 그 결과 폴더명 하나가 어긋났을 뿐인데 8종의 검사가 조용히 멈춘 채 정상 신호를 냈습니다.

### 막을지 말할지는 근거가 정합니다

같은 위반이라도 **어떻게 알아냈는지**에 따라 처리가 다릅니다.

| 근거 | 처리 | 예 |
|:--|:--|:--|
| **직접 봤음** — 검사기가 위반을 뱉었거나 파일이 실제로 거기 있음 | 차단 | 규칙 위반, 정리 안 된 산출물 |
| **추측했음** — git 상태로 "끝났을 것"을 미루어 판단 | 경고만 (막지 않음) | 작업 사본·작업 목록 정리 알림 |

추측으로 막으면 틀렸을 때 빠져나갈 길이 없습니다. 실제로 그런 일이 있었습니다 — 방금 만든 작업 사본을 "다 끝났으니 지우라"고 요구하거나, 아직 병합 전인 작업 기록을 지우라며 세션을 끝내지 못하게 붙잡았습니다. 지금은 **검출은 계속하되 문은 잠그지 않습니다.**

### 어떤 것들을 잡아주나요

저장 시 선택한 언어의 대상 파일을 검사하며 종료 시 미추적 소스까지 검사합니다. 전체 목록과 판정 근거는 `dev/HARNESS.md`에 있습니다. 대표 예시입니다.

| 잡히는 것 | 왜, 어떻게 고치나 |
|:--|:--|
| 분류되지 않은 제품 코드 | 컴포넌트와 역할을 사용자에게 제안합니다 |
| 화면 코드에 색상값 하드코딩 (`#ff8800`) | 색상 정본 파일이나 CSS 변수를 거치도록 |
| 고정 픽셀 너비 (`width: 420px`) | 모바일이 깨집니다. `max-width`·`%`·`clamp`로 |
| 한 파일 400줄 초과 | 단일 책임 상실. 기능 단위로 분할 |
| 소스에 API 키 하드코딩 | 설정 모듈 경유. 이미 커밋됐다면 키 회전까지 |
| 문서에 적힌 파일 경로가 실존하지 않음 | 삭제·이름변경 후 남은 참조 정리 |
| 공개 함수의 타입힌트 누락 | 모듈 경계면 명세화 |
| AI 에이전트 정의와 모델 정책표 불일치 | 모델 배정이 정책과 어긋나지 않게 |
| API는 만들었는데 그 화면이 없음 | 사용자에겐 없는 기능입니다. 화면까지가 한 단위 |
| 이름만 바꿔 다시 만든 함수 | 이미 있는 정본을 쓰거나, 공용으로 뽑아 한 벌만 |
| 상수 이름을 바꾸고 한 곳을 놓침 | 실행은 되고 그 화면을 눌러야 터집니다. 저장 시점에 잡습니다 |
| 함수 하나가 80줄 초과 | 파일 상한이 못 보는 축. 함수도 단일 책임 |
| 프론트 로직·컴포넌트에 테스트 짝 없음 | 타입체크·빌드는 값이 틀린 것을 못 잡습니다 |
| 새 화면 문구에 내부 용어·축약 은어 | 금칙어 명단 밖 신종은 세션 종료 시 AI 감수가 잡습니다 |

지원되는 런타임에 훅을 연결하고 신뢰한 경우 다음 시점에 검사합니다.

| 시점 | 대상 | 위반 시 |
|:--|:--|:--|
| 편집 도구 실행 직후 | 편집한 파일 | 위반 피드백, 수정 요구 |
| 세션 종료 시도 | 전체 | 세션 종료 차단 |
| 수동 실행 (`python -X utf8 -m kernel.runner`) | 전체 | 종료 코드 1 |

### 프로젝트 구조

[하네스 지도](dev/HARNESS.md)는 실행 경계와 검사 계약을 설명합니다.
업무 구조는 [컴포넌트 정본](dev/COMPONENTS.md)과 생성된 기능 지도에서 확인합니다.
허용 관계와 코드에서 관측한 관계를 구분하며 관측 결과로 허용 목록을 자동 확장하지 않습니다.

### 프로젝트 시작 서식

배포 서식은 스택 미정인 `_template` 하나입니다.
AI가 사용자에게 언어와 업무 분류를 제안하고 선택 결과에 따라 검사를 연결합니다.
이미 승인한 분류 안에서는 계속 자율적으로 개발합니다.
새 컴포넌트나 경계가 필요할 때만 변경안을 다시 묻습니다.
호스트 전용 알림 API 없이 AI가 대화로 알립니다.
로컬 승인 기록은 변경안과 답변의 일관성을 검증하며 사용자 인증을 제공하지 않습니다.

### 수동 설치

세션을 거치지 않고 직접 설치하려면:

```bash
python -X utf8 harness_install.py --list                      # 프리셋 목록 확인
python -X utf8 harness_install.py --preset _template  # 설정 파일 생성
# harness_profile.py 의 LANG·CHECK_PATHS 와 컴포넌트 그래프를 실물에 맞춘 후
python -X utf8 harness_install.py --doctor                    # 언어팩이 위임하는 외부 도구 설치 여부
python -X utf8 harness_install.py                             # 설정과 코드 검증
python -X utf8 setup_global_permissions.py                    # 전역 권한 병합
```

사전 요구사항은 Git 저장소(필수 — 검사 대상을 `git ls-files`로 모으므로 미초기화 시 전 검사가 헛돕니다), GitHub 원격(필수 — 미설정 시 세션 종료가 막힙니다), Python 3.10 이상(필수 — 미만이면 세션 시작 때 경고가 뜹니다), Node.js(선택 — UI 품질 점검 시)입니다.

### 기존 프로젝트에 도입하기

서식 2는 실행하지 않습니다.
기존 분류를 사용자와 검토하여 서식 3의 컴포넌트 그래프로 이전합니다.
설치 과정은 사용자 코드와 그래프 정본을 삭제하거나 현재 위반을 자동 동결하지 않습니다.
기존 baseline은 검사와 파일 단위라 같은 파일의 새 위반도 숨길 수 있습니다.
그래프 검사는 이 baseline으로 면제하지 않습니다.

```bash
python -X utf8 harness_install.py --dry-run
python -X utf8 harness_install.py --prune
```

### 검사 규칙을 늘리는 방법

장애나 작업 실수가 생기면 이 절차로 규칙이 늘어납니다.

| 단계 | 하는 일 | 남는 것 |
|:--:|:--|:--|
| 1 | 사고 경위와 손실을 기록합니다. 대가를 함께 적어야 다음 세션이 예외로 넘기지 않습니다 | `dev/LESSONS.md` |
| 2 | 기계로 검출할 수 있는지 판단합니다 | — |
| 3 | 가능하면 검사로 구현합니다. 범용 규칙은 `kernel/`, 이 저장소 전용은 `harness_gates/` | 검사 모듈 |
| 4 | 불가능하면 "산문 전용"과 사유를 명시합니다 | `dev/LESSONS.md` |

3도 4도 안 하면 그 자체를 검사가 잡습니다. 판단을 미룬 상태이기 때문입니다.

### 정기 점검 — 도구가 때를 알려줍니다

프로젝트가 커지면 문서·코드 불일치, 과설계, 미처리 부채가 쌓입니다. 이 도구는 저장소 실물에서 임계치를 재서 점검 시점을 스스로 판단하고, 세션 시작 때 알려줍니다. 진행 중인 작업이 끝나면 자동으로 돌고, 모든 점검은 보고서만 만들 뿐 소스를 건드리지 않습니다. 임계치는 `harness_profile.py`의 `MAINTENANCE`에서 조정합니다.

### Claude를 여러 개 띄워서 개발하고 싶다면

프로젝트가 커지면 욕심이 생깁니다. 화면은 이 세션에, API는 저 세션에 맡기고 동시에 달리게 하고 싶죠. 그런데 그냥 띄우면 언젠가 사고가 납니다 — 하나의 작업 폴더를 여럿이 쓰다가 서로의 작업을 덮어쓰고, 어느 날 남의 커밋에 내 코드가 쓸려 들어갑니다.

이 도구에는 그 사고를 실제로 겪고 다듬어진 협업 규약이 들어 있습니다. 세션마다 격리된 작업 사본을 받아 각자 거기서 작업하고, git 머지로 합칩니다. 그리고 늘 그렇듯 — 규약은 부탁이 아니라 **차단**으로 지켜집니다.

- 작업 사본 이름에 세션 표식이 자동으로 박힙니다. 목록 한 번이면 "지금 누가 뭘 하는지"가 보입니다.
- 작업 사본이 하나라도 생기는 순간, 공유 폴더에서는 커밋·add·브랜치 전환·머지가 자동으로 막힙니다. 병렬이 시작됐다는 뜻이니까요.
- 검사를 피해 셸로 몰래 소스를 고치는 것, 검사 결과가 나오기 전에 머지해버리는 것 — 실행되기 전에 막힙니다.
- 끝난 작업 사본을 안 치우면 세션을 끝낼 때마다 경고가 뜹니다. 막지는 않습니다 — "끝났다"는 판단이 추측이라서요. "나중에 정리"는 오지 않는다는 걸 도구가 압니다.
- 설계가 서로 겹치지 않는 3갈래 이상으로 나뉘면, 지휘 전담 AI가 파일 소유권을 나눠 여러 AI를 동시에 굴립니다.

혼자 한 세션으로 쓸 때는요? 이 전부가 조용히 잠들어 있습니다. 병렬을 시작하는 순간에만 깨어납니다.

### AI 모델 역할 분담

작업 성격에 따라 모델 등급을 나눠 씁니다. Opus·Fable 배정은 에이전트 정의가 정책표와 대조되는 검사 대상이라, 어긋나면 세션이 끝나지 않습니다. Sonnet 은 에이전트 정의 없이 팬아웃 호출 때만 지정합니다.

| 모델 | 담당 | 기준 |
|:--|:--|:--|
| **Opus** | 아키텍처 설계, 판단, 검수 | 되돌리기 비싼 판단. 등급 하향 없음 |
| **Fable** | 승인된 설계서의 전체 구현 | 판단이 끝나고 작업량만 남은 단계 |
| **Sonnet** | 다중 파일 정독·대조 | 판단 폭이 좁고 처리량이 큰 작업 |

### 검사기 자체 검증

검사기를 고치다가 특정 검사가 조용히 죽는 회귀를 막기 위해, 검사 항목별 위반을 하나씩 심은 픽스처와 그 검사 결과 정답지를 갖고 있습니다.

```bash
python -X utf8 tests/run_golden.py          # 전체 설정 기준 대조
python -X utf8 tests/run_golden.py --bare   # 설정 부재 기준 대조
```

현재 출력과 정답지가 다르면 그 행을 보고합니다. 검사기 리팩터링은 이 대조 통과가 기준입니다.

### 아키텍처 그림 — 검증되는 그림만 그림입니다

그림 넷은 문서 맨 위 「한눈에 보기」에 있습니다. `docs/architecture/`에 구조·흐름·시퀀스 그림의 정본(JSON)과 렌더된 HTML·SVG가 함께 있습니다. 규칙 지도는 손으로 그리지 않고 `python -X utf8 -m kernel.diagram rules`가 훅 배선과 게이트 목록에서 만듭니다. 상자마다 실제 소스 파일과 행 범위가 박혀 있고, 뷰어에서 상자를 누르면 그 코드가 열립니다. 검사 48이 세션 종료와 전량 검사 때 그림과 실물을 대조합니다 — 파일 이름을 바꾸고 그림을 안 고치면 세션이 끝나지 않습니다. 구조를 바꾸는 설계서에는 변경 전후 그림(델타)이 붙습니다. 렌더 엔진은 저장소 안에 들어 있어 보는 쪽은 아무것도 설치하지 않습니다.

```bash
python -X utf8 -m kernel.diagram validate architecture docs/architecture/<이름>.architecture.json
python -X utf8 -m kernel.diagram deliver  architecture docs/architecture/<이름>.architecture.json
```
